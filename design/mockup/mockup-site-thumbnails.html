图
前 → 后。
话
一句决定（C 的那句引号），加一句让它难的问题。
强
扫一眼的人从图里拿到思路，从引号里拿到高光；那一句难点留给想知道「怎么做到」的人点进去。
弱
话最短，每一句都要磨准。

推荐

版本三。它把 C 的决定留下，图负责让人一眼看懂高层的解法，最后那一句难点负责勾人点进去。版本一最勾人，适合你更在意点击率的时候；版本二最省力，适合不打算认真写案例页的时候。完整的理由在 spike。

Case 1 of 3 · Internal tool · WePay

A legacy tool nobody wanted to touch

Adding one panel to the risk team's dashboard took three teams. I didn't rewrite it in one go. I made the new code grow inside the old one.

Role
Primary owner; proposed it and designed the framework
Team
Risk tools
Users
The risk team, reviewing accounts by hand
Stack
Angular → React
When
To confirm

The problem

Adding one panel took three teams.

The risk team reviewed accounts in an internal dashboard that contractors had built in Angular. The rest of the company had moved to React. The UI was nested more than ten layers deep, and adding a panel took a backend config change, a production database script run by SRE, and new access rules in the backend. Almost no one wanted to touch it.

What got hard

The fix was obvious. The risk wasn't.

A React rewrite had been floated before and gone nowhere. A rewrite would freeze the tool the risk team used every day, and it asked managers to bet on a long project with nothing to show until the end.

How I thought

I chose to grow React inside the old app over a big-bang rewrite.

Rewrite it all at onceconsidered

Clean result, but a long freeze, one big cutover, and no value until the end.

Grow React inside the old appchosen

Replace from the leaves up. Both stacks run side by side; every panel ships on its own.

I flattened the ten-plus layers into App → Dashboard → Panel, and moved panel configuration and visibility to the frontend. To PM and managers I framed it as no UX change, no API change, and an incremental rollout, and pitched it until it was approved.

“A legacy system nobody wants to touch often hides real opportunity, and you can only migrate it once you understand exactly how it works.”

What changed

Panels went out in parallel, and engineers came back.

UI changes no longer needed production database scripts, and access rules ran in the frontend. With docs, examples, knowledge-transfer sessions and a live proof of concept, I handed more than twenty panels to teammates to build in parallel. Engineers started contributing to the tool again.

What I kept

An investment, not a task.

I treated the framework as a long-term investment, not a one-off task. It paid off later: when a module of an even older system failed in production, I rebuilt it on this framework and shipped it with SRE.
