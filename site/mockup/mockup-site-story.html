Four decisions, and the problems that made them hard.

One from the product I build for myself. Three from WePay and JPMorgan Chase, where I built end to end.

一 · Mars Workbench · my own product, 2025 – now

“A plan is negotiated, not generated.”

I turned a whiteboard a friend and I kept into a weekly planner. The AI wizard I built for it drafted the week in one shot, and I kept correcting it. It didn't know me.

So I deleted my own wizard and connected the board to Claude, the assistant I already work with every day. It reads my week, asks what to change, and writes only after I agree.

The product story

Before this

For years I built the same thing for other people: tools that show someone where they stand and what to do next.

For a risk team, for partners, and for merchants, at WePay and JPMorgan Chase.

二 · Internal tool · WePay

“I didn't rewrite it all at once.”

The risk team's review dashboard was an Angular app more than ten layers deep. Adding one panel took a config change, a production database script and new backend rules. A full React rewrite had been floated and stalled.

I grew React inside the old app instead, replacing it from the leaves up. No downtime, no UX change, no API change: that got managers to say yes, and let me hand panels out in parallel.

三 · Merchant-facing · WePay

“I questioned the design on paper.”

Large partners timed out downloading their transactions, so we moved to emailing a link. The planned design added a hop, and the email flow under it was spread across repos, tied to a retiring monolith, and owned by no one.

I proposed one path and one schema for every email. A new email became configuration. When that schema later broke a shared pipeline, I traced it to the root and ran the review.

Read the case

四 · Platform, 0 → 1 · JPMorgan Chase

“I locked the contracts before the APIs existed.”

One new portal had to replace several, for every kind of merchant. Its parts were built and deployed by different teams, and the onboarding APIs were still changing.

I built the shell that loads each part at runtime, checked every contract at runtime, and designed onboarding as one list of tasks that always says what comes next. When the first bank partner arrived, it needed little rework.

Case 1 of 3 · Internal tool · WePay

A legacy tool nobody wanted to touch

Adding one panel to the risk team's dashboard took three teams. I didn't rewrite it in one go. I made the new code grow inside the old one.

The problem

Adding one panel took three teams.

The risk team reviewed accounts in an internal dashboard that contractors had built in Angular. The rest of the company had moved to React. The UI was nested more than ten layers deep, and adding a panel took a backend config change, a production database script run by SRE, and new access rules in the backend. Almost no one wanted to touch it.

What got hard

The fix was obvious. The risk wasn't.

A React rewrite had been floated before and gone nowhere. A rewrite would freeze the tool the risk team used every day, and it asked managers to bet on a long project with nothing to show until the end.

How I thought

I chose to grow React inside the old app over a big-bang rewrite.

Rewrite it all at onceconsidered

Clean result, but a long freeze, one big cutover, and no value until the end.

Grow React inside the old appchosen

Replace from the leaves up. Both stacks run side by side; every panel ships on its own.

I flattened the ten-plus layers into App → Dashboard → Panel, and moved panel configuration and visibility to the frontend. To PM and managers I framed it as no UX change, no API change, and an incremental rollout, and pitched it until it was approved.

“A legacy system nobody wants to touch often hides real opportunity, and you can only migrate it once you understand exactly how it works.”

What changed

Panels went out in parallel, and engineers came back.

UI changes no longer needed production database scripts, and access rules ran in the frontend. With docs, examples, knowledge-transfer sessions and a live proof of concept, I handed more than twenty panels to teammates to build in parallel. Engineers started contributing to the tool again.

What I kept

An investment, not a task.

I treated the framework as a long-term investment, not a one-off task. It paid off later: when a module of an even older system failed in production, I rebuilt it on this framework and shipped it with SRE.
